## 2. Architecture in one page

```
catalog.sql   ──► db.js ──► sql.js (vendored in vendor/) ──► in-browser SQLite
     │                                                              │
     │                                            every page queries it directly
     │                                                              ▼
     └──► admin.html (edits a localStorage draft)          page rendering
                                                               │
catalog.json  ──► the Android app fetches this (no SQLite in Dart) │
```

There is no backend and no build step on the serving side. The root HTML files
are generated by `node build.mjs` and committed, so Pages serves a branch
directly.

The admin panel writes to `localStorage` under `alexstore.catalogDraft.v3`.
Visitors never see a draft. Publishing means downloading `catalog.sql` **and**
`catalog.json` and committing both.

## 3. Key decisions, and why

**WhatsApp is the only purchase path.** No cart, no account, no checkout. Every
product button, the drawer and the footer link to `wa.me/923288304524` with the
product, price and description pre-written into the message. The announcement
strip says only the delivery threshold — the CTA was removed as redundant
noise, since WhatsApp appears everywhere else.

**PKR only, integer paisa.** `price_cents: 780000` = Rs 7,800. No currency
selector, no USD anywhere, no floats.

**No CDN in the critical path.** sql.js was originally loaded from jsDelivr. It
silently hung (`initSqlJs()` never settled) and rendered the storefront blank
with no error. It is now vendored in `vendor/` with SHA-256 hashes recorded in
`db.js`. The only remaining CDN request is the search model, which is
best-effort with its own retry.

**Product vectors are precomputed.** Visitors embed only their query; product
embeddings ship inside `catalog.sql`. Adding a product without rebuilding the
index breaks search globally.

**Plain dot-product ranking.** The earlier BM25/IDF weighting was removed — it
is meaningless across dense embedding dimensions. Vectors are L2-normalised.

**Zero dependencies, deliberately.** Astro/11ty/Next.js were all considered and
rejected for the page build in favour of a ~180-line `build.mjs` using only
Node's standard library. Next.js specifically: GitHub Pages can only host a
static export, which forfeits SSR, ISR, server actions and middleware — the
actual reasons to want it. A package manager has nothing to manage until there
is a dependency tree.

**Three description fields, not one.** `description` is the one-line version on
cards, in search and in the WhatsApp message. `details` is the long copy on the
product page. `specs` is JSON label/value for the specifications box. Only
`description` is embedded, so only it needs an index rebuild.

**Product page = three regions.** Product, a Specifications box to its right on
desktop, and a scrollable Full description box beneath. The image height is set
by the grid row so it matches the specs box exactly (verified delta 0 at six
widths). The scroll region only gets `tabindex` when it actually overflows.

**Grid uniformity is enforced by CSS, not discipline.** `.product__name`
reserves two lines, `.product__desc` three, and `margin-top: auto` on the price
pins everything to the card bottom. Text that exceeds that is clamped with an
ellipsis and always available in full on the product page.

**Hero is sized to the viewport.** `min-height: calc(100svh - var(--sticky-h))`,
so it lands whole on a first visit at every width measured. Short viewports
(≤700px tall) get a compacted type scale, because `min-height` sets a floor and
cannot compress content.

**Only verifiable claims.** The About page states nothing that isn't true of how
the store actually works — no invented founding year, sourcing story or
location. The Journal ships empty with an honest empty state rather than
invented posts. The spec values in `catalog.sql` are explicit placeholders.

**APK comes from GitHub Releases, not Pages.** A Pages site serves one repo, and
an APK committed to the repo is permanent in git history. Releases assets are
outside the tree, so they cost nothing. Use the `latest` release tag so the URL
never changes again.

**The refund policy lives in `db.js`, and reaches every product twice.** The
wording is one constant, `REFUND_POLICY`. `toJson()` appends its note to every
product's `details` in `catalog.json`, which is how the policy gets in front of
someone who already has the app installed: the app renders exactly three
per-product text fields, and `details` is the only one of them that is neither
embedded for search nor pasted into the WhatsApp message, so nothing else could
carry it without a re-index or a new APK. Appending on export rather than storing
it in the `products` table is what keeps a product added next month from missing
it, and keeps the shop's own copy clean.

The product page does not read it from the data. `product.js` renders the same
constant as its own small note, and strips the appended copy out of `details`
first, so a shopper reads the sentence once instead of twice. The About page
carries the full wording, including the cancellation fee, as hand-written static
copy — deliberately not generated from the constant, because a policy should
still be readable if a script fails. **That makes the About page and the constant
a matched pair: change the fee or the window in one and change it in the other.**
The product page and the app cannot drift apart, because they read the constant.

## 4. Things that have actually bitten

Each of these cost real debugging time.

**The index has two failure modes, only one of them warns you.**

| Change | Skipping the rebuild causes |
| --- | --- |
| Added a product | `indexIsComplete()` → false; `search.js` returns `[]`; **every search returns nothing, site-wide** |
| Edited name/category/description | Completeness stays **true**; search silently matches against the **old** text |

**A schema change touches four places, not one.** `toSql()` embeds its *own
copy* of the `CREATE TABLE` (inside a template literal — no backticks allowed
in those comments) and its own hardcoded `INSERT` column list. Patching only
`catalog.sql` produced an export whose `INSERT` supplied 11 values against a
9-column header — every publish would have shipped a broken catalog. Verify by
replaying the export into a fresh sql.js database, not by reading the diff.

**The root HTML is generated.** Edit `src/`, then `node build.mjs`. Bump
`version` in `build.config.json` for any `.js`/`.css` change; the build injects
it into every tag on every page. `admin.html` is excluded from the build.

**`db.js` has mixed line endings** (`\n`, `\r\n`, and `\r\r\n`). Plain text
replaces silently fail. Patch with Node using single-line anchors.

**`ResizeObserver` fires zero callbacks in a background iframe** — even for a
forced 54→66px change — because it needs a paint. Never rely on it alone.

**Pages need `Store.init()` even with no product list**, or the announcement bar
shows a stale string and every WhatsApp link stays `href="#"`. This bug
shipped once on the About page and was dismissed as a screenshot timing
artefact. It was not.

**The sticky chrome is measured, not hardcoded.** The announcement bar wraps to
two lines below ~400px, changing its height. `common.js` must call
`syncStickyOffsets()` after rewriting it. When it didn't, the hero overran the
first screen by exactly 19px and the header docked under the bar on scroll.

**320×568 is the tightest viewport.** The hero has ~4px of slack there. Adding
a second stacked hero button pushed it over; short-viewport rules now trim
button height and gaps.

**PowerShell `Set-Content -Encoding utf8` writes a BOM** that makes
`JSON.parse` fail on an invisible character. `build.mjs` strips one.

**Safari/iOS: none verified.** All testing has been Chromium on desktop
emulation. Not a single iOS device has been checked.

**A third-party licence file at the root makes GitHub mislabel the whole repo.**
This repository had no `LICENSE` and no badge, which was harmless. Committing the
sql.js notice without thinking would not have been: GitHub's licence detector
reads a root file whose name looks like a licence as *the repository's* licence,
so `THIRD_PARTY_SQLJS_LICENSE` would have made GitHub report this storefront as
MIT - and here it would have been believed, because this repository really does
contain MIT-licensed code. That is why `LICENSE` (all rights reserved) and
`THIRD_PARTY_NOTICES.md` landed together, in that order, and why the notice is
deliberately not named like a licence. Recorded here rather than only in the app
repository's MEMORY because it is this repository that would suffer it next.

## 5. Publishing checklist

```bash
# admin.html: edit → Build search index → Download catalog.sql
#              → Download catalog.json
# replace both in the repo
# any .js/.css change? bump version in build.config.json, then:
node build.mjs
node build.mjs --check        # must exit 0 before pushing
node --check <each edited .js>
git add -A && git commit && git push
# wait ~60s for the Pages build
```

After pushing, verify on the live URL — not locally: 8 products,
`Catalog.indexIsComplete()` true, search returns results, grid uniform, every
WhatsApp link resolves, Lighthouse a11y 1.0.

- [ ] No CI. `node build.mjs --check` would fail a stale commit if wired into a
